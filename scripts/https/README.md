# VWSHub HTTPS Installer

Отдельный компонент для WVW на Debian/Ubuntu: локальный CA, сертификат с DNS/IP SAN, Apache 2.4 или Nginx, перенаправление HTTP → HTTPS, защищённые cookie и пакет доверия Windows. Рабочее приложение остаётся на **127.0.0.1:5000**. Данные, пароли, камеры, права, архив и настройки HEVC установщик не редактирует.

Компонент использует прежние имена `vwshub-*` для совместимости. Репозиторий: [sedukindv/WVW](https://github.com/sedukindv/WVW); внешнее имя приложения — WVW.

## Подготовка и первый запуск

Нужен действующий Waitress `app:app` под systemd, привязанный только к 127.0.0.1:5000. Поддерживаются системная служба и служба пользователя из прежнего README. Установщик проверяет MainPID, `/proc/<pid>/cmdline`, каталог с `app.py`/`hub/core.py`, владельца пользовательской службы и PID фактического слушателя 5000. Неизвестные процессы не останавливаются. Интерактивный Waitress, контейнеры и нестандартный supervisor автоматически не переписываются: сначала оформите проверяемую systemd-службу.

Скачайте полный проверенный исходный архив релиза или клонируйте репозиторий по HTTPS. Сохраните целостность **всей** папки `scripts/https`, включая Windows-скрипт. Не используйте скачивание с немедленным исполнением через `curl | sh`.

Из корня проекта:

```sh
sudo sh scripts/https/install.sh install
```

Появятся запросы DNS и IPv4 с примерами `srv-vms.bk-base.local` / `172.17.6.155`. Введите `-`, чтобы не включать один из вариантов. Хотя бы один SAN обязателен. Для автоматизации:

```sh
sudo sh scripts/https/install.sh install \
  --dns-name srv-vms.bk-base.local --ip-address 172.17.6.155 \
  --app-service vwshub.service
```

Служба systemd пользователя:

```sh
sudo sh scripts/https/install.sh install \
  --dns-name srv-vms.bk-base.local --ip-address 172.17.6.155 \
  --app-service vwshub.service --app-user operator
```

Для стандартных имён `vwshub.service` / `wvw.service` выполняется автоопределение. `--app-dir /полный/путь/проекта` дополнительно сверяет рабочий каталог процесса. Пользовательская служба должна уже иметь рабочую шину `/run/user/<uid>/bus`; её lingering/запуск настраивает оператор согласно своей установке. Установщик не создаёт новую службу WVW и не меняет её ExecStart.

DNS проверяется через системный resolver. Если имя не указывает на заданный IP, потребуется явное `YES`. В неинтерактивном режиме используется `--allow-dns-mismatch` после проверки предупреждения. Это разрешает выпуск SAN, но не настраивает DNS: добавьте корректную запись в DNS/клиентский hosts до доступа по имени. IP-only и DNS-only поддерживаются отдельными `--ip-address` / `--dns-name`.

Bootstrap устанавливает недостающие Python 3, OpenSSL, ca-certificates и iproute2 из настроенных APT-репозиториев Debian/Ubuntu. Если веб-сервера нет, устанавливается Apache; при существующем Apache/Nginx второй сервер не устанавливается. Для двух установленных, но неактивных серверов выберите `--proxy apache` или `--proxy nginx`. Два одновременно активных proxy, неизвестный владелец 80/443, пересечение имён, regex-server_name или некорректная исходная конфигурация требуют ручного разбора; чужие сайты не заменяются.

Firewall установщик **не меняет**. Оператор отдельно согласует доступ клиентов к 80/443; порт 5000 остаётся внутренним. Для DNS/IP сертификата не требуются Cloud ID, публичный DNS или ACME.

## Что устанавливается

| Путь | Назначение |
| --- | --- |
| `/etc/vwshub/pki/rootCA.key` | Закрытый ключ CA, root:root, 0600; никогда не выдаётся клиентам. |
| `/etc/vwshub/pki/rootCA.crt` | Публичный корневой сертификат. |
| `/etc/vwshub/pki/versions/<id>/server.key` и `server.crt` | Пары серверного ключа/сертификата; ключ 0600. |
| `/etc/vwshub/pki/current` | Атомарно переключаемая ссылка на проверенную пару. |
| `/etc/vwshub/https/state.json` | Параметры установки, без приватных ключей; root-only. |
| `/etc/vwshub/https/backups/<id>/journal.json` | Защищённый снимок изменяемых файлов/ссылок и их режимов для отката. |
| `sites-available/zz-vwshub-https.conf` и ссылка в `sites-enabled/` выбранного proxy | Только сайт WVW, отмеченный владельцем Installer. |
| `vwshub-https.conf` в drop-in каталоге проверенной службы | Только `COOKIE_SECURE=1`, `VWSHUB_TRUST_PROXY=1`. |
| `/usr/local/sbin/vwshub-https` | Установленная команда управления. |
| `vwshub-https-renew.service` / `.timer` | Ежедневная проверка продления с задержкой до часа. |
| `/root/vwshub-https-client-package/` | Только публичный CA, PS-скрипт, инструкция, отпечаток и HTTPS-адрес. |

Закрытые каталоги PKI и state доступны root. Публичные сертификаты имеют 0644, но выдаются сотрудникам через отдельный **публичный** пакет, не через открытие всего PKI. Apache/Nginx должны работать со стандартным root master, читающим ключ до запуска непривилегированных workers.

WVW 0.9.0 доверяет ровно одному forwarded proto/host/port hop только при `VWSHUB_TRUST_PROXY=1` и loopback REMOTE_ADDR. Proxy перезаписывает эти заголовки, передаёт запросы только на loopback, отключает буферизацию потокового Nginx-ответа и использует 900-секундные таймауты. CSRF и Origin validation остаются включёнными. После проверенного рестарта службы установщик проверяет HTTPS с собственным CA и SAN, а также реальный Secure/HttpOnly session cookie страницы входа/первичной настройки.

## Сертификаты и повторный запуск

При первой установке создаётся RSA CA (по умолчанию 10 лет), затем серверный сертификат с явными SAN и serverAuth. Проверяются ключ, цепочка, срок действия, точные DNS/IP и `CA:FALSE`. CN не подменяет SAN.

Повторный `install` использует тот же исправный CA и действующий серверный сертификат с теми же SAN, если до истечения больше 30 дней. Конфигурации не дублируются. Для применения cookie drop-in служба приложения перезапускается только после проверки её личности и синтаксиса proxy. Повторная установка может кратковременно переподключить действующие сессии/потоки.

Обычный `renew` **никогда не создаёт новый CA**. Отсутствующий/повреждённый/истёкший CA вызывает отказ без замены действующей пары. Сертификат сервера не выпускается на срок дольше оставшегося срока CA. При приближении конца жизни самого CA организуйте отдельную плановую смену доверия клиентов; удаление ключа и повторный install не являются безопасным продлением.

При повторном выпуске сначала создаётся новая пара в отдельном закрытом каталоге, проверяется, затем атомарно меняется `current`, проверяется конфигурация и выполняется reload proxy. WVW при продлении не перезапускается. При ошибке возвращается прежняя ссылка и конфигурация; служба timer завершится с ошибкой, видимой в journal. Старые пары и root CA сохраняются для восстановления.

## Команды

```sh
sudo vwshub-https status
sudo vwshub-https renew
sudo vwshub-https renew --if-expiring
sudo vwshub-https export-ca
sudo vwshub-https uninstall
```

`status` только читает состояние: DNS/IP/HTTPS-адрес, сертификат/срок, SHA-256 CA, proxy, timer, пакет и результат HTTPS/cookie-проверки. Для проверки соответствия закрытым ключам требуется root; непроверенное/ошибочное состояние не называется успешным. Команда не создаёт каталогов, lock-файлов и не перезагружает службы.

`renew` принудительно перевыпускает листовой сертификат; `--if-expiring` ничего не меняет до 30-дневного порога. `export-ca` заново формирует пакет с **нормализованным PEM только сертификата**, а отпечаток считается по DER X.509. Даже combined PEM не копируется как исходный файл. Файл `rootCA.crt` с приватным ключом не допускается при установке: разделите публичный сертификат и закрытый ключ до продолжения.

Журналы:

```sh
sudo systemctl status vwshub-https-renew.timer
sudo systemctl list-timers vwshub-https-renew.timer
sudo journalctl -u vwshub-https-renew.service -n 100
```

## Клиентский пакет Windows 10/11

Передавайте всю папку `/root/vwshub-https-client-package/` по аутентифицированному защищённому каналу, например корпоративному SFTP/системе развёртывания. Пакет содержит только `rootCA.crt`, `install-vwshub-ca.ps1`, `README.txt`, `SHA256.txt`, `connection.json`. Не копируйте `rootCA.key`, `server.key` или весь `/etc/vwshub/pki`.

Отпечаток CA сообщите отдельно через доверенный канал/непосредственно с консоли сервера. `SHA256.txt` из того же скачивания служит сверкой содержимого, но сам по себе не доказывает подлинность. Проверенный отпечаток сертификата также не удостоверяет изменённый злоумышленником PowerShell-скрипт: защищённая доставка пакета и политика подписи скриптов организации сохраняются.

На клиенте откройте PowerShell **от администратора** в папке пакета:

```powershell
.\install-vwshub-ca.ps1 -CertificatePath .\rootCA.crt `
  -ExpectedFingerprint ОТПЕЧАТОК_SHA256_С_СЕРВЕРА `
  -Url https://srv-vms.bk-base.local
```

Скрипт проверяет администратора, один публичный PEM-сертификат, отсутствие приватного ключа, дату, Basic Constraints `CA:TRUE`, KeyCertSign и цепочку. Показывает SHA-256, сверяет ожидаемое значение и требует ввести `TRUST`. В `LocalMachine\Root` добавляется именно проверенный **in-memory** X.509 объект, без повторного чтения изменяемого файла после подтверждения. Повторный запуск не добавляет дубликат; после установки сверяется отпечаток. Другие доверенные сертификаты не удаляются. Без администратора работа прекращается без обхода Windows или политики организации.

Chrome/Edge используют системное доверие Windows. После установки откройте показанный HTTPS-адрес и проверьте цепочку/имя сайта. Самоподписанный локальный CA не считается автоматически доверенным до установки доверия на клиенте.

Firefox может использовать корни ОС или отдельную корпоративную политику; проверьте актуальные настройки организации. Современный Firefox поддерживает доверие к корням ОС, однако поведение может ограничиваться политикой/настройками. [Mozilla: доверие сторонним корневым сертификатам](https://support.mozilla.org/en-US/kb/automatically-trust-third-party-certificates).

На iOS/iPadOS вручную установленному профилю может потребоваться отдельное включение полного доверия SSL/TLS; для организаций предпочтительно MDM. [Apple: доверие установленному профилю](https://support.apple.com/en-ie/102390). На Android установка пользовательского CA зависит от устройства и политики; приложения могут не принимать пользовательские корни. Используйте руководство своей версии/MDM, а не Windows-скрипт. [Google: добавление сертификатов](https://support.google.com/pixelphone/answer/2844832?hl=en), [Android: доверенные CA приложения](https://developer.android.com/privacy-and-security/security-config).

## Обновление компонента

Сохраните root-only копии `/etc/vwshub/pki`, `/etc/vwshub/https` и текущей версии компонента в защищённом offline-хранилище. Обновите весь `scripts/https` из проверенного релиза и повторите `sudo sh scripts/https/install.sh install` с прежними SAN/службой. CA не удаляйте: его замена требует нового доверия на каждом клиенте. Установленная команда/Windows helper будут обновлены; текущая исправная пара сохранится до необходимости продления.

## Удаление и восстановление

`uninstall` удаляет только помеченные собственные site/drop-in/timer файлы и перезагружает проверенные службы после проверки синтаксиса. CA, закрытые ключи, версии сертификатов, backup-журналы, клиентский пакет и установленная команда сохраняются. Пакеты Apache/Nginx и общие включённые модули не удаляются: их могут использовать другие сайты. Созданный Installer общий Listen 443 также сохраняется, если его используют посторонние HTTPS VirtualHost. Уже остановленный proxy автоматически не запускается. Доверие CA на Windows не отзывается автоматически — это отдельная административная операция по точному отпечатку, а не очистка всех корней.

Для возврата **предыдущей конфигурации этого же размещения**:

```sh
sudo vwshub-https uninstall --restore-backup /etc/vwshub/https/backups/НОМЕР_КОПИИ
```

Указывается каталог, напечатанный в `last_backup` при install. Восстанавливаются прежние собственные конфигурации и согласованная ссылка сертификата/состояние; чужие сайты не перезаписываются. Копия другого proxy/службы/пользователя/каталога приложения автоматически не применяется. Сохранившаяся HTTPS-конфигурация проходит проверку сертификата, синтаксиса и HTTPS перед включением timer. Если копия относится к первой установке, результатом будет отсутствие установленного сайта при сохранении CA для дальнейших действий.

При ошибке install/renew файлы возвращаются автоматически из журнала транзакции. Если новая среда не дала WVW запуститься, после восстановления drop-in повторно запускается только ранее проверенная systemd unit с неизменённым хешем определения и свободным портом 5000 — даже при MainPID=0. Изменённая/неизвестная служба не запускается; выводится сообщение о необходимости внимания. APT-установку пакетов автоматический файловый откат не отменяет. Исходные CA/ключи никогда не отправляются в публичный отчёт.

При ручном аварийном восстановлении сначала остановите timer, сохраните текущий PKI/state отдельно и используйте защищённую копию того же размещения. Не удаляйте CA ради устранения ошибки сертификата и не копируйте root key клиентам. Проверяйте причину в journal и обычным `status`; `curl -k` не является проверкой корректности TLS. Изменения firewall согласуйте отдельно.

## Риски локального CA

Доверенный корневой CA может подписывать сертификаты имён сайтов. Компрометация `rootCA.key` затрагивает все устройства, доверившие ему корень. Храните его root-only, резервную копию — зашифрованно/offline, с ограниченным кругом администраторов. При компрометации нужен отзыв/удаление **именно этого** корня на клиентах, новый CA и контролируемое повторное развёртывание доверия. Ротация листового сертификата это не исправляет.

## Тесты и границы проверки

Из корня проекта в Linux CI (без запуска installer main и без изменения служб):

```sh
python3 -m pip install -r requirements.txt -r requirements-dev.txt
openssl version
python3 -m pytest tests/test_https_installer.py -q
sh -n scripts/https/install.sh
```

Тесты используют временный каталог **вне продукта**, имитации systemd/ss/proc/APT, реальные OpenSSL сертификаты при доступном CLI и отдельную проверку DER/fingerprint/combined PEM через cryptography. Реальная установка через main, импорт Windows trust и рестарт реальных служб в этих тестах не выполняются; путь status проверяется с подменённым Installer. На Windows криптографический CLI-тест пропускается, если OpenSSL принципиально не запускается; POSIX symlink/permission сценарий требует Linux.

В текущей среде разработки фактически пройдены mock/validation/rollback тесты и PowerShell parser; полноценная установка Apache/Nginx в Debian/Ubuntu и фактический импорт Windows Root **не выполнялись**. Git OpenSSL здесь блокируется sandbox (`signal pipe / Win32 error 5`), а Windows symlink недоступны. Пропущенные проверки не считаются пройденными. Перед производственным применением выполните Linux OpenSSL roundtrip и стендовый deployment в вашей systemd/proxy среде, затем отдельно Windows-клиент. Итоги конкретной сборки фиксируются в основном отчёте.
